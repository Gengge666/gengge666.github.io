我的 Python 日常工具链（2026 版）

2026 年 2 月 27 日 ·约 9 分钟 ·你的名字

我折腾环境的时间一度比写代码还多：pip 装到一半报编译错误、 两个项目要用不同版本的同一个库、换了台电脑就忘了当初装了什么。 后来我把这套流程压缩成三条命令，从此新项目十分钟内就能进入写代码的状态。

一、原则：工具要少，且各管一件事

  • uv —— 管解释器、虚拟环境和依赖。
  • ruff —— 管格式与静态检查（它同时替代了 black、isort、flake8）。
  • pytest —— 管「我的假设是否成立」。

就这三样。像 poetry、pyenv、pre-commit 这些不是不好， 而是在我目前的项目规模下，多一层抽象就多一处会坏的地方。

二、新项目：四条命令起步

bash 
uv init demo && cd demo        # 生成 pyproject.toml 与 .python-version
uv add numpy pandas             # 写入依赖并锁定 uv.lock
uv add --dev pytest ruff        # 开发依赖单独分组
uv run python main.py           # 在项目环境里执行，无需手动 activate

关键在于 uv run：它会在执行前确保环境与 uv.lock 一致， 于是「我本机明明能跑」这类问题基本消失了。uv.lock 应该提交到 Git， .venv/ 不应该。

三、目录结构：够用就好

text 
demo/
├── pyproject.toml        # 依赖与工具配置的唯一入口
├── uv.lock               # 锁定精确版本，提交进 Git
├── README.md
├── src/
│   └── demo/
│       ├── __init__.py
│       ├── data.py       # 读取与清洗，保持纯函数
│       └── model.py
└── tests/
    └── test_data.py

用 src/ 布局的好处是：测试必须通过安装后的包来导入， 而不是靠「当前目录恰好能被 import」的假象。这个差别在小项目上不明显， 一旦开始打包就会救命。

四、把配置集中到 pyproject.toml

toml 
[tool.ruff]
line-length = 100
target-version = "py311"

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]   # 语法错误、导入顺序、现代化写法、易错模式
ignore = ["E501"]                     # 行长交给 formatter 处理

[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-q"

日常只需要两条命令：

bash 
uv run ruff format .      # 格式化
uv run ruff check --fix . # 静态检查并自动修可修的部分
uv run pytest             # 跑测试

关于 ruff 我的建议是：一开始只用默认规则集。 我曾经一次性打开了几十条规则，结果每次保存都在修无关紧要的告警， 最后把整个配置注释掉了。规则应该一条一条加，每条都要知道为什么加。

五、五个真实的坑

1. 不要在系统 Python 里装包

macOS 与多数 Linux 发行版都开始保护系统解释器，直接 pip install 会报 externally-managed-environment。这不只是限制，而是在提醒你： 项目依赖就该待在项目里。

2. 相对导入只在包内有效

直接 python src/demo/model.py 去跑一个用了 from .data import load 的文件，必然失败——因为你运行的是脚本而不是模块。正确方式是 uv run python -m demo.model，前提是包已安装。

3. 可变的默认参数

python 
# 错误：默认值只在函数定义时创建一次，会跨调用累积
def collect(item, bucket=[]):
    bucket.append(item)
    return bucket

collect("a")   # ['a']
collect("b")   # ['a', 'b']  ← 不是 ['b']

# 正确
def collect(item, bucket=None):
    bucket = [] if bucket is None else bucket
    bucket.append(item)
    return bucket

4. 浮点数不能直接比相等

0.1 + 0.2 == 0.3 是 False。用 math.isclose(a, b, rel_tol=1e-9)，或者在测试里写 pytest.approx(0.3)。

5. 打印调试不如日志

一旦代码跑到服务器或长循环里，print 就没有级别、没有时间戳、没法关闭。 早点换 logging，代价只有几行：

python 
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s",
)
log = logging.getLogger(__name__)

log.info("开始处理 %d 条样本", n)

六、什么时候该加工具

我给自己定的触发条件很具体，避免为了「专业感」堆工具：

触发条件才引入
有第二个人参与项目pre-commit 钩子、PR 模板
需要定时或分布式跑任务调度框架、容器化
训练任务超过一小时实验追踪与断点续跑
同一个 bug 犯了三次写测试，而不是写注释

小结

工具链的终点不是「我的配置比你的复杂」，而是从想法到可运行代码的延迟足够短。 现在我的延迟大概是十分钟：四条命令建项目，写函数，写一个测试，跑通，提交。 剩下的时间才真正花在问题上。
